# Irregularities ledger (flagged & audited for review)

Every anomaly, upstream discrepancy, portal edge case, and data-hygiene risk encountered across the GEMSDOE68 lineage and the S68 v3 three-pass upgrade is explicitly recorded below with its root cause, exact workspace evidence, and mitigation status.

| **IR-68-PORTAL-01** | DrivenData upload form previously rejected certain GeoTIFFs with `"Predicted values must be in range [0, 1]"` despite valid `[0, 1]` inside-footprint values. | Two independent root causes identified and permanently resolved in `validate_portal_ready()`: **(1) Footprint mismatch (`3,061` cells):** `sample_submission.tif` has `5,167,373` finite cells whereas `training_features.tif` band 1 has `5,165,852` finite cells (`3,061` cells in `sample_submission` had `NaN` features — naively predicting only on `fp_feat` wrote `3,061` unexpected `NaN`s inside `sample_submission`!). **(2) NaN-blind portal check (`np.all((arr >= 0) & (arr <= 1))`):** returns `False` if ANY pixel anywhere is `NaN`. Primary recommended upload `GEMSDOE68-O2AC-MultiPhys-v3-20261020T201500Z-zeros.tif` sets `outside_fill=0.0` (`nan_total = 0`, all `12,279,160` cells finite in `[0.0, 1.0]`, matching how the `0.2778` live champion was uploaded), accompanied by `-nan.tif` (`fp_union`, `nan_in_sample_sub = 0`) and `-strict-nan.tif` (`16/16` `gems.validate_submission`). | **RESOLVED & TESTED** (`tests/test_o2_autocontext68.py`, `tests/test_s68_submission_and_runcard.py`) |
